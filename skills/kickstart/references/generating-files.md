## Template resolution

Templates live in this skill's `templates/` directory. Files are stored without a leading dot (`gitignore`, `editorconfig`, `claude/settings.json`) so they stay visible and are not picked up by tools; write them with the dot (`.gitignore`, `.editorconfig`, `.claude/settings.json`).

For each output file, in order:

1. `templates/<stack>/<file>` exists: use it.
   - `gitignore`: **append** the stack file to `_base/gitignore` (base first).
   - `editorconfig`: **append** the stack file's sections after `_base/editorconfig`; a stack section for the same glob wins.
   - Any other file (for example `claude/settings.json`): **replace** the base file.
2. Otherwise use `templates/_base/<file>`.
3. `templates/<stack>/stack.md` is not an output file. It feeds commands, conventions and permissions into the others.

Templates contain `{{PLACEHOLDERS}}` and an HTML comment with instructions. Fill every placeholder from the design, the repo and `stack.md`; delete a section that would only hold a guess; remove the instruction comment.

## Per-file rules

**CLAUDE.md** (`_base/CLAUDE.md`)
- At most 80 lines. Shorter is better.
- Commands follow the "Real beats default" rule in SKILL.md. Include install, build, test, single test, lint and run where they exist; drop a line when neither the repo nor `stack.md` gives a command that would work here (for example no `start` script means no run line).
- Structure: the real top-level tree. Directories the design plans but that don't exist yet are marked `(planned)`.
- Conventions: only the three to six rules an agent would get wrong without being told. Everything else stays in `docs/CONVENTIONS.md`, linked.
- The Superpowers line appears only when Superpowers is installed (see `superpowers.md`).
- The UI block appears only when the design-system step ran; the frontend-design mention in it only when that skill is installed.

**docs/ARCHITECTURE.md**: what is decided, from the design and the repo. Unknowns go under "Open questions", not into made-up components.

**docs/CONVENTIONS.md**: start from the `stack.md` Conventions list, then add what the design or existing code establishes. Name the formatter or linter instead of restating its rules.

**docs/decisions/0001-\<kebab-title\>.md**: one ADR for the design's main decision, usually the stack or the architecture approach. Title is a short imperative ("Use SQLite for local storage"). Options come from the approaches considered in the design; if none were (the stack was fixed before the kickstart), write that under Options instead of inventing alternatives. Date is today.

**README.md**: for humans. What it is, requirements, how to run and test, links to the docs. A runtime version goes in only if the repo pins one (`engines`, `.nvmrc`, `global.json`, `rust-toolchain.toml`, `requires-python`, ...).

**.gitignore / .editorconfig**: as resolved above. Drop rules for tools the repo does not use (for example `.next/` in a CLI). Keep the "Generated by" header in a new file; leave it out when appending to an existing one.

**.claude/settings.json**
- Start from the stack's `claude/settings.json`; match the entries to the commands actually written in `CLAUDE.md` (for example swap `npm` for `pnpm`).
- `allow` holds only read-only git commands and the exact build, test, lint, format and type-check commands. Add each one twice, bare and with arguments: `Bash(<command>)` and `Bash(<command> *)`.
- Never allow: wildcards over a whole tool (`Bash(npm *)`, `Bash(git *)`), package installs or publishes, package runners that can download (`npx`, `pnpm dlx`, `uvx`), `rm`, `git push`, `git reset`, `git clean`, `curl`/`wget`, or anything that deploys. `git push` stays in `ask`.
- Keep the `deny` entries for `.env` and `secrets/`.
- Personal overrides belong in `.claude/settings.local.json`, which the base `.gitignore` excludes.
- Claude Code treats `.claude/settings.json` as a protected file and may ask for approval or block the write, even when other edits are auto-accepted. If it is blocked, show the full content in your reply and ask the user to approve the write; don't save it anywhere else in the repo.

## Existing files

Never write over a file that exists, including one created earlier in this session by someone else.

1. Read it.
2. Prepare the smallest change that brings in what the template adds (for example, missing ignore rules appended under a `# Added by project-kickstart` comment), keeping everything the user wrote.
3. Show it as a unified diff and ask: apply, skip, or write the generated version to `<file>.kickstart` for them to merge.
4. Do only what they pick.

An existing `CLAUDE.md` or `AGENTS.md` is the user's: propose additions, never a rewrite. If only one of the two exists, offer to create the other from it.

## AGENTS.md: symlink or copy

Write `CLAUDE.md`, then:

- **macOS, Linux, WSL:** `ln -s CLAUDE.md AGENTS.md` from the repo root (relative target, so it survives clones).
- **Windows (native):** copy the file. Add this line at the top of `AGENTS.md` only: `<!-- Copy of CLAUDE.md; keep both in sync. -->`
- If symlink creation fails anywhere, fall back to the copy.

## Checks after generating

Run these and fix failures before reporting:

1. `wc -l CLAUDE.md` is 80 or less.
2. No `{{` left in any generated file (`grep -rn '{{' <generated files>`).
3. Every relative link in `CLAUDE.md` and `README.md` points to a file that exists. A link to a file the user dropped from the list is removed, not left dangling.
4. `.claude/settings.json` is valid JSON (`python3 -m json.tool .claude/settings.json` or `node -e "JSON.parse(require('fs').readFileSync('.claude/settings.json','utf8'))"`).
5. `AGENTS.md` resolves to the same content as `CLAUDE.md` (`diff CLAUDE.md AGENTS.md`, ignoring the Windows copy header).
6. If dependencies are installed (the scaffold step installed them, or they already were), run the build, test and lint commands once and report each result. Do not install dependencies only to run checks.
